# 晨间签到

此技能**每天触发一次**，随机在工作日开始前的两小时内触发，如果不知道用户的工作日开始时间，则在当地时间的早上 7 点到 9 点之间触发。默认的 7am–9am 窗口在安装时已写入 `.claude/scheduled_tasks.json`——一旦用户在 `CLAUDE.md` 中填写了 Catch-up 时段，就将该 cron 条目重写为在实际开始时间前两小时（cron 使用本地时间，因此直接使用本地小时即可）。你在 fork 上下文中运行——`CronCreate` 等工具调用会执行并持久化到磁盘，但**主智能体唯一能看到的是你的最终文本**。在最终文本中构建摘要；主智能体决定是否转发。

读取 `CLAUDE.md` 了解用户是谁（姓名、时区、代号）以及 `.claude/catch-up-state.json` 了解你已经在跟踪的内容。

---

## 现在还是早上吗？

cron 固定了你的预期触发时间，但调度器会在延迟启动时追赶——笔记本电脑整夜关闭，下午 3 点打开 → 你会在下午 3 点触发。此时不要生成简报；catch-up 已经运行了数小时，今天的情况已经覆盖了。

根据 `CLAUDE.md` 中的 Catch-up 时段开始时间检查本地时间（如果为空则默认为上午 9 点）。如果距离工作开始时间**超过两小时**，则仅以一行结束：

```
(not morning)
```

主智能体不会转发此内容。不要扫描任何内容，不要写入状态。

对于 9am 工作开始时间，在 9:30am 触发是没问题的（在窗口内——简报仍然有用）。在 11:30am 触发则不行（catch-up 已经覆盖了）。如果用户在非正常时间手动运行你，主智能体会看到 `(not morning)` 返回，并可以通过告知用户情况来覆盖——这由它决定。

## 阶段 1 —— 日历

**仅在连接了日历工具时执行。** 如果没有，跳到阶段 2。

拉取今天的事件（用户本地时区，从工作开始到当天结束）。对于每个事件，记录：

- **标题、时间、参会者**
- **你的回复状态**——如果你尚未 RSVP，标记出来。
- **准备信号**——描述中是否提到了文档、议程、演示文稿、预读材料？参会者列表是否暗示这是一个需要你提供内容的评审会议？这是一个你通常需要准备内容的周期性会议？
- **手头材料**——搜索文档/网盘，查找与事件标题匹配或邀请中链接的内容。我们有草稿吗，还是什么都没有？

### 调度会前签到

对于每个有具体开始时间的事件，调度一个一次性提醒，在事件开始前整理好材料。为每个事件选择一个**2 到 15 分钟之间**的随机偏移量（每个事件不同——不要让所有提醒堆在同一个偏移量上）。从事件的本地开始时间中减去偏移量，然后：

```
CronCreate(
  cron: "<minute> <hour> <day-of-month> <month> *",   # 本地时间，固定
  prompt: "/pre-meeting-checkin <标题> · <本地时间> · <参会者> · <任何文档链接或准备说明>",
  recurring: false
)
```

使用 `recurring: false`——这些任务触发一次后自动删除。先执行 `CronList`，跳过任何已经调度了匹配的会前提示的事件（如果用户手动重新运行你，或 catch-up 已经先处理了某个事件，不要重复预订）。

## 阶段 2 —— 过夜收件箱

扫描自上一个工作日结束以来到达的内容。仅使用实际已连接的工具——自行适配。

- **邮件**——来自重要人物或域名的未读邮件（老板、下属、关键协作者——`CLAUDE.md` 和 `catch-up-state.json` 中的优先级告诉你谁重要）。不是全量收件箱扫描——选取今天真正需要关注的 3-5 封。
- **聊天**——提及、私信、有你参与的活跃话题。同样的筛选标准：今天需要回复的内容 vs. 背景噪音。
- **文档**——自昨天以来分享给你的新文档，或你拥有的文档上的评论/编辑。

每一项一行：发送者/作者、主题、为什么今天重要。

---

## 阶段 3 —— 今日轮廓

根据日历密度 + 收件箱信号 + `catch-up-state.json` 中的优先级，推断出今天**最需要做好的一件事**。一个需要准备的会议、一个截止日期、一个等待你回复的话题。

如果存在一个自然的检查点——截止日期前一小时、一段空闲时间结束后——调度它：

```
CronCreate(
  cron: "<minute> <hour> <day-of-month> <month> *",   # 本地时间，固定
  prompt: "Check-in: <事项>。进展如何？有什么阻碍？",
  recurring: false
)
```

不要过度调度。零个或一个此类提醒。Catch-up 每两小时运行一次，如果情况有变会注意到。

将今天的首要任务写入 `catch-up-state.json` 的 `priorities` 字段，以便 catch-up 能获取到。

---

## 阶段 4 —— 简报

你的最终文本就是摘要。这是主智能体看到并转发的内容。**简洁。可扫读。有层次。**

```
**<星期, 日期>** · <N> 场会议 · <M> 件事需要你

**日历**
  <时间>  <标题>  <· 未回复 | · 需要准备 | （无标记则正常）>
  <时间>  <标题>

**需要你**
  · <发送者/话题> — <一行说明>
  · <发送者/话题> — <一行说明>

**首要任务：** <那件最重要的事>

<我可以：为 X 起草议程 / 为 Y 准备幻灯片 / 回复 Z。告诉我选哪个。>
```

任何为空的段落直接省略。如果日历为空且没有任何事项需要用户关注，整个简报就三行。目标是用户扫一眼就能了解今天的大致情况——而不是让他们读一份报告。

在周末没有安排且收件箱为空时，整个简报一行即可：`**<星期>** · 无事。` 不要凭空编造工作来汇报。

一次性会前签到已经调度好了——不要在简报中列出它们，它们会自行触发。
