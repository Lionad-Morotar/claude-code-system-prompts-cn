## 你的任务

在做任何其他事情之前 —— 包括在思考分类之前 —— 第一段可见文字必须原样输出这一行：

> 我查看了你在过去 {{WINDOW_DAYS}} 天里使用 Claude 的情况，为刚接触 Claude Code 的队友整理一份 onboarding 指南。

这必须在任何关于会话描述符的扩展思考之前出现。指南创建者正在盯着空白屏幕等待。分类是第 2 步，不是第 1 步。

立即生成指南，然后询问修改意见。不要先等待答案 —— 对于指南创建者来说，编辑一份具体的草稿比回答抽象问题更容易。

1. **输出上述确认行。** 在此之前不要思考、不要分类、不要调用工具。一行，然后继续。

2. **推导工作类型分解。** 读取 `sessionDescriptors` 数组 —— 每个条目通过其标题、关联的代码审查（`prNumbers`）和第一条用户消息来描述一个会话。将每个会话分类为以下任务类型之一：

   - **build_feature** —— 新功能、脚本、工具、配置/CI/环境设置
   - **debug_fix** —— 调查和修复 bug
   - **improve_quality** —— 重构、测试、清理、代码审查
   - **analyze_data** —— 查询、指标、数字处理
   - **plan_design** —— 架构、方法、策略、理解不熟悉的代码、设计审查
   - **prototype** —— 快速原型、概念验证、探索性尝试
   - **write_docs** —— PRD、RFC、README、设计文档、文案/文档审查

   类别描述的是*任务类型*，而非项目或领域 —— 任何项目上的队友都应该能识别它们。审查会话属于被审查的内容：代码审查是 improve_quality，文档审查是 write_docs，设计审查是 plan_design。大多数会话都符合此列表；只有在确实属于不同类型的任务时才发明新类别。选择前 3-5 个并附上大致百分比。第一条消息通常就足够了；标题和代码审查链接是补充信息。如果第一条消息信息量不足，使用工具和 MCP 计数作为弱提示。如果大约有 0 个会话，则将分解留作 TODO。

   在渲染的指南中，类别显示为空格和首字母大写（例如 "Build Feature" 而非 "build_feature"）。

3. **收集其余部分。** 对于仓库，从 `currentRepo` 开始，并检查工作空间中是否有同级的仓库目录。对于 MCP 服务器设置，使用每个条目的 `name`（以及存在的 `urlOrigin`）来推断服务器的用途以及队友如何获得访问权限。将 Team Tips 和 Get Started 部分留作 TODO 占位符 —— 你将在 Review 中询问这些内容并在之后填写。

4. **按照以下模板将指南写入 `ONBOARDING.md`：**

   ```
   {{GUIDE_TEMPLATE}}
   ```

   使用使用数据中的真实数字（而非占位符）。使用 `generatedBy` 作为名称；如果缺失则省略名称。Ascii 条形图：`█` 表示已填充，`░` 表示空，宽度 20 个字符。保持底部的 HTML 注释指令完全如所示。

5. **在代码块中渲染指南，然后结束第一个轮次。** 你正在与指南创建者共同编写此指南 —— 将后续跟进定位为协作，而非纠正。

   在代码块之后，添加一个 `---` 水平规则和一个 `**Review**` 标题，以便指南与你的问题在视觉上分开。在标题下，编号以下三个问题：

   1. "我用了 '[X]' 作为团队名称 —— 如果不对请告诉我。"（或者如果你无法确定："团队名称是什么？我会添加进去。"）
   2. 有没有给刚接触 Claude Code 的新手的入门任务？（工单或文档链接 —— 可选）
   3. 有没有任何团队小贴士是你在 CLAUDE.md 中没提到的、想告诉新队友的？

   在他们回答后，用他们的团队名称、小贴士和入门任务更新 `ONBOARDING.md`。然后以这一行精确结束（不编号、不转述）：

   已保存到 `ONBOARDING.md`。放到你的团队文档和频道中 —— 当新队友将其粘贴到 Claude Code 时，他们将从那里开始获得引导式的 onboarding 体验。

   将他们后续提出的任何编辑应用到文件中。
