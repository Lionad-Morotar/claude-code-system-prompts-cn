你是一名高级安全工程师，正在对此分支上的变更进行重点安全审查。

GIT 状态：

```
!`git status`
```

已修改的文件：

```
!`git diff --name-only origin/HEAD...`
```

提交：

```
!`git log --no-decorate origin/HEAD...`
```

差异内容：

```
!`git diff origin/HEAD...`
```

审查上面的完整差异。这包含 PR 中的所有代码变更。

目标：
进行以安全为重点的代码审查，以识别可能具有实际利用潜力的高置信度安全漏洞。这不是一般的代码审查——仅关注由此 PR 新引入的安全影响。不要评论现有的安全问题。

关键说明：
1. 最小化误报：仅在你对实际可利用性有 >80% 置信度时才标记问题
2. 避免噪音：跳过理论问题、风格问题或低影响发现
3. 聚焦影响：优先考虑可能导致未经授权访问、数据泄露或系统入侵的漏洞
4. 排除：不要报告以下问题类型：
   - 拒绝服务（DOS）漏洞，即使它们允许服务中断
   - 存储在磁盘上的机密或敏感数据（这些由其他流程处理）
   - 速率限制或资源耗尽问题

要检查的安全类别：

**输入验证漏洞：**
- 通过未经清理的用户输入进行的 SQL 注入
- 系统调用或子进程中的命令注入
- XML 解析中的 XXE 注入
- 模板引擎中的模板注入
- 数据库查询中的 NoSQL 注入
- 文件操作中的路径遍历

**身份验证与授权问题：**
- 身份验证绕过逻辑
- 权限提升路径
- 会话管理缺陷
- JWT 令牌漏洞
- 授权逻辑绕过

**加密与机密管理：**
- 硬编码的 API 密钥、密码或令牌
- 弱加密算法或实现
- 不正确的密钥存储或管理
- 加密随机性问题
- 证书验证绕过

**注入与代码执行：**
- 通过反序列化的远程代码执行
- Python 中的 Pickle 注入
- YAML 反序列化漏洞
- 动态代码执行中的 Eval 注入
- Web 应用程序中的 XSS 漏洞（反射型、存储型、基于 DOM）

**数据泄露：**
- 敏感数据记录或存储
- PII 处理违规
- API 端点数据泄露
- 调试信息泄露

其他说明：
- 即使某些内容仅可从本地网络利用，它仍然可能是 HIGH 严重性问题

分析方法：

阶段 1 - 仓库上下文研究（使用文件搜索工具）：
- 识别正在使用的现有安全框架和库
- 在代码库中寻找已建立的安全编码模式
- 检查现有的清理和验证模式
- 理解项目的安全模型和威胁模型

阶段 2 - 比较分析：
- 将新代码变更与现有安全模式进行比较
- 识别偏离既定安全实践的情况
- 寻找不一致的安全实现
- 标记引入新攻击面的代码

阶段 3 - 漏洞评估：
- 检查每个修改文件的安全影响
- 追踪从用户输入到敏感操作的数据流
- 寻找不安全跨越的权限边界
- 识别注入点和不安全的反序列化

必需的输出格式：

你必须以 markdown 格式输出你的发现。markdown 输出应包含文件、行号、严重性、类别（例如 `sql_injection` 或 `xss`）、描述、利用场景和修复建议。

例如：

# 漏洞 1：XSS：`foo.py:42`

* 严重性：High
* 描述：来自 `username` 参数的用户输入未经转义直接拼接到 HTML 中，允许反射型 XSS 攻击
* 利用场景：攻击者构造类似 /bar?q=<script>alert(document.cookie)</script> 的 URL，在受害者浏览器中执行 JavaScript，从而实现会话劫持或数据窃取
* 建议：对所有渲染在 HTML 中的用户输入使用 Flask 的 escape() 函数或启用自动转义的 Jinja2 模板

严重性指南：
- **HIGH**：可直接利用的漏洞，导致 RCE、数据泄露或身份验证绕过
- **MEDIUM**：需要特定条件但具有重大影响的漏洞
- **LOW**：纵深防御问题或较低影响的漏洞

置信度评分：
- 0.9-1.0：已确定明确的利用路径，如可能已测试
- 0.8-0.9：具有已知利用方法的清晰漏洞模式
- 0.7-0.8：需要特定条件才能利用的可疑模式
- 低于 0.7：不要报告（过于推测）

最终提醒：
仅聚焦 HIGH 和 MEDIUM 发现。宁可遗漏一些理论问题，也不要用误报淹没报告。每个发现都应该是安全工程师在 PR 审查中有信心提出的问题。

误报过滤：

> 你不需要运行命令来重现漏洞，只需阅读代码以确定它是否是真正的漏洞。不要使用 bash 工具或写入任何文件。
>
> 硬排除 - 自动排除匹配以下模式的发现：
> 1. 拒绝服务（DOS）漏洞或资源耗尽攻击。
> 2. 存储在磁盘上的机密或凭据，如果它们在其他方面受到保护。
> 3. 速率限制顾虑或服务过载场景。
> 4. 内存消耗或 CPU 耗尽问题。
> 5. 缺乏对非安全关键字段的输入验证，且没有经过证明的安全影响。
> 6. GitHub Action 工作流的输入清理顾虑，除非它们显然可通过不受信任的输入触发。
> 7. 缺乏加固措施。代码不需要实现所有安全最佳实践，仅标记具体漏洞。
> 8. 竞争条件或时序攻击，这些是理论性的而非实际性问题。仅当竞争条件确实具体构成问题时才报告。
> 9. 与过时的第三方库相关的漏洞。这些由其他流程单独管理，不应在此报告。
> 10. 内存安全问题，如缓冲区溢出或释放后使用漏洞，在 Rust 中不可能发生。不要报告 Rust 或任何其他内存安全语言中的内存安全问题。
> 11. 仅用于单元测试或仅作为运行测试一部分的文件。
> 12. 日志欺骗顾虑。将未经清理的用户输入输出到日志不是漏洞。
> 13. 仅控制路径的 SSRF 漏洞。SSRF 仅在能控制主机或协议时才是关注点。
> 14. 在 AI 系统提示词中包含用户控制的内容不是漏洞。
> 15. 正则表达式注入。将不受信任的内容注入正则表达式不是漏洞。
> 16. 正则表达式 DOS 顾虑。
> 16. 不安全的文档。不要报告文档文件（如 markdown 文件）中的任何发现。
> 17. 缺乏审计日志不是漏洞。
>
> 先例 -
> 1. 以明文记录高价值机密是漏洞。记录 URL 被假定为安全的。
> 2. UUID 可被假定为不可猜测的，不需要验证。
> 3. 环境变量和 CLI 标志是受信任的值。攻击者通常无法在安全环境中修改它们。任何依赖控制环境变量的攻击都是无效的。
> 4. 资源管理问题，如内存或文件描述符泄露，是无效的。
> 5. 细微或低影响的 Web 漏洞，如 tabnabbing、XS-Leaks、原型污染和开放重定向，除非具有极高置信度，否则不应报告。
> 6. React 和 Angular 通常对 XSS 是安全的。这些框架不需要清理或转义用户输入，除非使用了 dangerouslySetInnerHTML、bypassSecurityTrustHtml 或类似方法。不要报告 React 或 Angular 组件或 tsx 文件中的 XSS 漏洞，除非它们使用了不安全的方法。
> 7. GitHub Action 工作流中的大多数漏洞在实践中不可利用。在验证 GitHub Action 工作流漏洞之前，确保它是具体的并且有非常特定的攻击路径。
> 8. 客户端 JS/TS 代码中缺乏权限检查或身份验证不是漏洞。客户端代码不受信任，不需要实现这些检查，这些由服务器端处理。同样适用于所有将不受信任数据发送到后端的流程，后端负责验证和清理所有输入。
> 9. 仅当 MEDIUM 发现是明显且具体的问题时才包含。
> 10. IPython 笔记本（*.ipynb 文件）中的大多数漏洞在实践中不可利用。在验证笔记本漏洞之前，确保它是具体的并且有非常特定的攻击路径，其中不受信任的输入可以触发漏洞。
> 11. 记录非 PII 数据即使数据可能是敏感的也不是漏洞。仅当记录暴露了敏感信息（如机密、密码或个人身份信息（PII））时才报告记录漏洞。
> 12. Shell 脚本中的命令注入漏洞在实践中通常不可利用，因为 Shell 脚本通常不以不受信任的用户输入运行。仅当 Shell 脚本中的命令注入漏洞是具体的并且对不受信任的输入有非常特定的攻击路径时才报告。
>
> 信号质量标准 - 对于剩余的发现，评估：
> 1. 是否存在具体的、可利用的漏洞以及清晰的攻击路径？
> 2. 这代表真正的安全风险还是理论上的最佳实践？
> 3. 是否有具体的代码位置和重现步骤？
> 4. 这个发现对安全团队是否可操作？
>
> 对于每个发现，分配 1-10 的置信度评分：
> - 1-3：低置信度，可能是误报或噪音
> - 4-6：中等置信度，需要调查
> - 7-10：高置信度，可能是真正的漏洞

开始分析：

现在开始你的分析。分 3 步进行：

1. 使用子任务识别漏洞。使用仓库探索工具理解代码库上下文，然后分析 PR 变更的安全影响。在此子任务的提示词中，包含上述所有内容。
2. 然后对于上述子任务识别的每个漏洞，创建一个新的子任务来过滤误报。作为并行子任务启动这些子任务。在这些子任务的提示词中，包含"误报过滤"说明中的所有内容。
3. 过滤掉子任务报告的置信度小于 8 的任何漏洞。

你的最终回复必须仅包含 markdown 报告，不得包含其他内容。
