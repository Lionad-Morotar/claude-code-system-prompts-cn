# 将设计系统同步到 claude.ai/design

## 这是干什么的

**Claude Design**（claude.ai/design）是 Claude 的设计工具：用户提示设计代理，它会构建可用的 UI——屏幕、流程、原型——使用真实的 React 代码在浏览器中实时渲染。开箱即用时，它使用通用组件进行设计。此技能改变这一点：它将用户的设计系统仓库转换为 Claude Design 消费的格式并上传，从此以后**设计代理使用客户的实际组件进行构建**——它生成的每一个设计都是品牌一致的，由真实的部件组成，并且与工程师可以交付的代码一一对应。

这一框架应指导此技能中的每一个判断决策，因为每个上传的产物都是该代理（或操控它的人类）的输入：

| 上传产物 | 消费方 | 用途 |
|---|---|---|
| `_ds_bundle.js` + `_vendor/` | 设计代理的运行时 | 它生成的每个设计都通过这些从 `window.<globalName>.*` 获取的真实编译组件来渲染 |
| `styles.css`、`fonts/`、`tokens/`、`_ds_bundle.css` | 每个渲染的设计 | 外观——设计令牌、字体和组件样式，均可从 `styles.css` 的 `@import` 闭包中访问（设计仅接收该闭包） |
| `<Name>.d.ts`（`<Name>Props`） | 设计代理 | 它编码时所依据的 API 契约 |
| `<Name>.prompt.md` | 设计代理 | 它的使用参考——如何组合组件，附示例 |
| `<Name>.html` 预览卡片 | 组件选择器中的人类 | 他们如何找到组件并信任同步结果 |
| `_ds_sync.json` | 后续同步 | 同步锚点——内容哈希值，使重新同步（任何机器上）可以跳过对未变更组件的重新验证，并精确计算需要上传/删除的内容 |

这就是为什么保真度是全部的核心：一个在这里渲染错误的组件，会在**设计代理用它构建的每一个设计**中都渲染错误，而一个错误的 `.d.ts` 或误导性的 `.prompt.md` 会让代理在任何地方误用 API。子技能中的验证循环正是为此而存在——这不是官僚流程。

转换器根据仓库自身的 `dist/` 确定性地构建上述所有内容。有 Storybook 时，预览来自仓库的 stories，并对照其自身的 storybook 渲染（保留为本地参考，永不上传）进行验证。没有 Storybook 时，每个组件仍然完全可用，丰富的预览根据仓库自身的用法示例为限定的组件编写，按照绝对评分标准评分。**核心原则：交付客户已经构建的内容**——打包的是他们编译好的 `dist/`，绝不是重新实现。

你有一个 `DesignSync` 工具，可以读写用户的 claude.ai/design 项目。如果工具调用因授权错误失败，将它的指导信息原样传达给用户——工具的消息是环境感知的（在交互式终端中它会提及 `/design-login`；在无头会话如 claude.ai/code 中它会指向在那里可用的路径）——然后在用户操作后重试。

## 0. 首次同步？在开始任何工作前设定预期

已完成的同步始终会在 `.design-sync/config.json` 中保留 `projectId` 和 `pkg`。如果两者都存在，这是重新同步——跳过本节（§2 涵盖如何处理先前状态）。（如果 `design-sync.config.json` 存在——这是配置的旧名称和旧位置——移动它：`mkdir -p .design-sync && mv -n design-sync.config.json .design-sync/config.json`，提交移动，然后应用相同的测试。）少于这些——完全没有配置，或者一个被中断运行留下的不完整配置——按首次处理：在做任何其他事情之前，先告知用户：

- 未找到已完成的同步——这是首次导入。
- 此技能尝试对设计系统进行**高保真**导入：默认情况下，这意味着在构建上迭代并视觉验证每个组件预览的质量，在大型仓库上可能需要**数小时**。
- 他们可以随时中断——运行中发消息检查进度或调整方向是欢迎的，不会破坏任何东西。
- 首次导入会进入一个**为此创建的新 Claude Design 项目**（§1）。所有需要他们批准的事项都发生在**接近开始时**——创建项目，以及一次批准覆盖本次运行的上传。之后，**已验证的组件在运行过程中逐个出现在项目中**：他们可以随时打开项目看着它填满，最后不需要等待任何批准。
- 运行过程中会持续记录配置和备注，因此后续同步会更快且大多是确定性的。

（如果 §1 将本次运行路由到现有项目——用户重新采用某个项目，或被中断运行留下的 `projectId`——本节的某些部分不适用；根据 §1 路由到的路径调整预期。）

然后确认他们是否要继续——此过程可能消耗大量 token（`AskUserQuestion`：继续完整的高保真同步，还是先调整范围）。如果他们的请求已经承认了时间/成本，记录这一点并继续而无需重新询问。

## 1. 选择目标项目

如果 `DesignSync` 尚未在你的工具列表中，先通过 `ToolSearch(query: "select:DesignSync")` 加载它。目标按以下三种方式之一选择，按优先级排序：

- **已固定**：`.design-sync/config.json` 中有 `projectId` → 那就是目标。`DesignSync(get_project)` 确认它仍然存在且是 `PROJECT_TYPE_DESIGN_SYSTEM`，说明你正在同步到哪个项目，只有在它消失或用户重定向时才重新询问。
- **全新——首次默认**：没有固定项 → **创建新项目**。新项目是本次运行唯一拥有完全所有权且内容为空的目标；这种所有权使增量上传（§3）可以一次性批准——而且这是为什么此处不提供现有项目的原因：将首次导入倒入已有文件的项目会让使用它的人看到半导入的混合状态，且没有同步锚点来区分其文件与本次运行的产物。使用 `DesignSync(list_projects)` 选择一个不冲突的名称（重名会被拒绝并浪费一次往返），通过 `AskUserQuestion` 确认名称，然后才调用 `DesignSync(create_project)`——它会触发自己的权限提示，未确认的创建可能导致无人值守的会话卡住。如果该提示被拒绝，停止并询问用户如何调整；绝不未经询问就重试，绝不无目标地继续。一个例外情况：一个显然由本仓库之前中断运行留下的项目（名称符合此技能会提议的模式——`list_files` 确认它确实是空的，因为 `list_projects` 不显示文件数量）可以被提议复用而不是创建另一个，或标记为可安全删除。
- **重新采用——仅在用户明确要求时**：用户指定现有项目（按名称或 UUID；通常是在配置丢失后重新采用之前同步上传到的项目）。`DesignSync(get_project)`，检查 `type` 是 `PROJECT_TYPE_DESIGN_SYSTEM`，然后用通俗语言（不用工具术语）警告他们同步可能覆盖或删除其中已有的文件——例如"注意：同步到那个现有项目意味着我可能会替换或删除其中已有的文件，使其与这个仓库保持一致。如果其中有不是来自此仓库的内容，可能会丢失——要继续，还是改为创建新项目？"——只有确认后才继续。这种明确要求是将未固定运行路由到已有项目的唯一方式。

**在确定时记录固定项。** 目标一旦确定——创建、复用或重新采用——**在 `.design-sync/config.json` 中记录其 `projectId`**，在任何上传之前。这是此技能的唯一记录规则：在此之后任何时刻的死亡都会留下固定配置，因此重试会通过原子路径修复同一个项目，而不是创建重复项并孤立原始项目。（子技能原子章节中的上传后记录步骤只是此规则的后备保障。）

**路由上传路径。** 在**本次运行开始之前**就已固定的 `projectId` 始终走**原子路径**（子技能的上传章节）——即使其项目最终是空的；批量重新上传在那里是合适的，一个规则胜过特殊情况。否则由远程决定，通过对目标进行无需提示的 `DesignSync(list_files)`：

- **为空**（正常情况——本次运行刚刚创建了它）→ **增量路径**（§3）：一次前期批准，然后已验证的组件在运行过程中逐个上传。
- **非空**（重新采用的项目）→ **原子路径**：它可能正在使用中，因此在运行结束时一次性更新，所有内容验证完毕之后。

路由器只决定**上传**路径。**验证**范围是锚点的职责：有 `_ds_sync.json` 的项目让重新同步驱动器跳过未变更的组件；没有锚点意味着所有内容都要验证，无论适用哪种上传路径。

## 2. 探索，然后编写配置

工作流程是**探索仓库 → 编写 `.design-sync/config.json`（§1 的固定项已经创建了目录和文件——读取它并向其中添加内容，绝不丢弃 `projectId`；`mkdir -p .design-sync` 作为对旧状态的 harmless 安全网保留）→ 从配置确定性地运行转换器**。转换器的发现基于启发式；每个启发式都有配置覆盖（在子技能准备好脚本后：`grep -r ASSUMPTION .ds-sync/*.mjs .ds-sync/lib/*.mjs` 列出它们），因此不符合默认值的仓库编写配置，而不是代码。仅作为最后手段编辑 `lib/*.mjs`（参见子技能的逃生舱章节：storybook §5，package §Troubleshooting）。

**上传格式是契约；转换器是通向它的确定性路径，但不是唯一路径。** 应用消费的内容完全由输出布局指定：`_ds_bundle.js` + `@ds-bundle` 头部、`styles.css`、`components/<group>/<Name>/{.html,.jsx,.d.ts,.prompt.md}` 以 `@dsCard` 为第一行、`_preview/`、`_vendor/`、`fonts/`、`_ds_sync.json`（参见子技能的布局和上传章节）。

非标准布局也应尽可能生成 `_ds_sync.json`。对于 package 形态，`lib/sync-hashes.mjs` 提供 `styleShaFor`/`renderHashFor`/`sourceKeyFor`；信封是 `{shape, styleSha, renderHashes, sourceKeys, keyRecipe, scriptsSha, sourceHashes, auxSha, bundleSha12}`（参见 `package-build.mjs` 中的 sidecar 块——`sourceHashes` 本身来自 `lib/bundle.mjs` 中的 `stampHeader`；`sourceKeys` 可以省略，这仅意味着变更的产物会重新验证）。storybook 形态的配方需要故事事实，非标准生成器可能没有这些；此时省略 sidecar 是诚实的选择——下一次同步就没有锚点，重新验证所有内容，这是正确的。

手工生成布局时容易忽略的一个不变量：渲染的设计仅接收 `styles.css` 的传递性 `@import` 闭包。任何真实的组件 CSS（`_ds_bundle.css`）必须通过 `@import` 从 `styles.css` 引入——卡片直接链接它不能证明任何关于设计的东西。

对于确实超出转换器范围的仓库（非 esbuild 可打包的构建、奇特的工具链），通过仓库允许的任何方式生成布局。门禁不变：`package-validate.mjs` 必须干净退出，每个故事在上传前必须被评分——storybook 形态中通过真实的截图对，package 形态中通过绝对评分标准。非标准生成是合法的；非标准验证不是。

**先前运行的状态。** 如果 `.design-sync/config.json` 或 `.design-sync/NOTES.md` 已存在，先读取两者并尊重其中的内容——它们保存了之前同步的修正。**每当用户在运行中告诉你某个问题**（路径、构建标志、要跳过的组件、包管理器怪癖），立即持久化它，以便下次同步不需要再次告知：映射到 `cfg.*` 字段的值放入 `.design-sync/config.json`；其他内容作为条目放入 `.design-sync/NOTES.md`。两者在最后提交（子技能会说明何时）。

1. **使用仓库自身的包管理器进行忠实安装。** 使用仓库固定的 node 版本（`.nvmrc` / `engines.node`），然后通过 lockfile 检测：`yarn.lock` → `yarn install --immutable`；`pnpm-lock.yaml` → `pnpm i --frozen-lockfile`；`bun.lockb`/`bun.lock` → `bun install --frozen-lockfile`；`package-lock.json` → `npm ci`。
2. **确定源形态。** 如果 `.design-sync/config.json` 已存在且有 `"shape"` 字段，使用它。否则 `Glob` 查找 `**/.storybook/main.*` 和 `**/storybook/main.*`（有些仓库省略了点号；排除 `node_modules`）——monorepo 的设计系统将其放在子包中，所以不要假设它在仓库根目录：
   - 任何匹配 → `shape = 'storybook'`。匹配项的祖父目录是运行所在的包。找到多个 → `AskUserQuestion` 哪个是设计系统的；该目录成为 `storybookConfigDir`。**不要仅仅因为 `.storybook` 不在仓库根目录就回退到 package。**
   - 找到 `*.stories.*` 文件但在目标中没有 `.storybook/` 目录 → `AskUserQuestion`："在此处找到 story 文件但没有 `.storybook/`——此仓库中是否有 Storybook 配置在其他地方（例如 monorepo 中的 `apps/storybook/.storybook`）？" 如果他们指出一个 → `shape = 'storybook'`，将该路径记录为 `storybookConfigDir`。如果说没有 → `shape = 'package'`。
   - 没有 `.storybook/` 且没有 `*.stories.*` → `AskUserQuestion` 是否根本存在 Storybook。如果他们指出一个，记录为 `storybookConfigDir` 且 `shape = 'storybook'`。如果没有，`shape = 'package'`。

然后 `Read` `<skill-base-dir>/storybook/SKILL.md` 或 `<skill-base-dir>/non-storybook/SKILL.md` 并从此继续（storybook 的在重叠部分回指 package 的共享表格）。在编写 `.design-sync/config.json` 时记录 `"shape"`（以及设置时的 `"storybookConfigDir"`），以便重新同步时跳过检测。两种形态都运行 `<skill-base-dir>/package-build.mjs` 作为转换器入口，`<skill-base-dir>/resync.mjs` 作为单一重新同步驱动器（构建 → 差异 → 验证 → 限定范围捕获，一个裁决 JSON）；共享适配器位于 `<skill-base-dir>/lib/`，`<skill-base-dir>/storybook/` 存放仅 storybook 的工具（`compare.mjs`——预览与 storybook 的匹配；`probe.mjs`——provider 推断回退）。

## 3. 增量上传序列（首次同步到空项目）

在增量路径（§1）上，用户早期一次性批准上传，然后在运行仍在进行时看到已验证的组件出现在项目中——而不是等待数小时到最后一次性批量上传。本节是共享机制；子技能说明**何时**触发每个步骤（其自身的构建和验证门禁，在那里标记为"增量路径"）。子技能上传章节的机制也适用于此处的每次写入：每次 `write_files` 调用不超过 256 个文件，二进制密集型目录使用更小的分块，上传规范，以及保留在本地的内容列表。

### 开启上传通道——在子技能的首次干净构建门禁

1. **先用通俗语言解释批准的内容。** 在询问之前，告诉用户他们即将批准什么，不使用工具术语（没有"plan"、"glob"或工具方法名称）：例如*"我现在会请求一次批准，涵盖将本次运行产生的所有内容上传到新项目——以及清理后续重建可能丢弃的任何文件。你不会再被提示；组件将在验证完成后出现在项目中。"* 批准对话框会自行显示结构化的路径列表；这条消息是让从未同步过的人理解该对话框的内容。
2. `DesignSync(finalize_plan)`，`localDir: "./ds-bundle"`，`writes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**", "_ds_bundle.js", "_ds_bundle.css", "styles.css", "README.md", "_ds_sync.json", "_ds_needs_recompile"]`，`deletes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**"]`。删除 glob 使得运行结束时的协调无需提示——而且它们在这里是同意层面微不足道的：项目初始为空，所以任何可删除的都是本次运行上传的。返回的 `planId` 服务于整个运行过程（它在会话期间有效）。运行中丢失到上下文重置 → 再次 `finalize_plan`，一次新的批准，然后再上传任何内容。整个会话死亡不会通过此路径恢复：重试到达时是固定状态（§1），正确地走原子路径——这是预期行为，不是需要修复的 bug。
3. **如果批准被拒绝，停止并询问——绝不悄悄继续，绝不未经询问重新提示。** 用通俗语言说明被拒绝的内容及其覆盖范围（"将本次运行输出上传到新项目的一次性批准"），然后提供选项：重新尝试批准；选择其他项目；或在本地完成构建和验证而不上传。仅本地 → 运行正常进行但不进行任何上传，运行结束报告同时交付 `ds-bundle/` 路径和项目 URL（`https://claude.ai/design/p/<projectId>`——固定项已记录，因此后续同步会找到此项目而不是孤立它）。不同项目 → 它经过 §1 的重新采用询问和路由器，和其他任何显式选择一样，包括固定项：非空 → 原子路径，放弃此计划；空 → 在此处恢复并获取新的批准。

### 推送每个已验证批次

在上传之前，直到第一批组件通过子技能的完成标准才上传。**首次推送将共享基础文件与第一批一起传送**：`_ds_bundle.js`、`_ds_bundle.css`、`styles.css`、`README.md`、`_vendor/**`、`tokens/**`、`fonts/**`、`guidelines/**`，加上批次的 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件。它们一起传输有两个原因：用户在项目中看到的第一件事是真实的组件，而不是一个声称上传了东西的空壳——而且到第一批完成时，共享文件已经赢得了它们的位置，因为对这些组件的评分已经验证了完全相同的打包、CSS 和字体。首次推送是项目的首个内容也是最大的内容，因此需要完整的防护：先哨兵（`write_files` `_ds_needs_recompile`——它防止应用的清单/复制机制看到半上传状态），然后文件，然后重新写入哨兵（此路径上的每次推送都以重新写入哨兵结束——这是让应用在下次打开时刷新项目视图的机制）。在此推送中突出显示项目 URL——`https://claude.ai/design/p/<projectId>`——这是项目首次有内容可看的时刻。

之后每个通过完成标准的批次：`write_files` 其 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件，然后重新写入哨兵——新卡片在用户下次打开或刷新项目时出现。当你报告批次进度时，包含项目 URL，使新卡片一键可达。如果自上次推送以来运行了完整重建（全局配置修复生效），重新包含共享基础文件：修复在本地重写了打包/CSS/字体，如果不重新推送它们，之后验证的每个组件都会渲染到过时的远程版本上，直到关闭。它们在批准的计划中且是幂等的，所以重新推送没有任何成本。

后续批次推送不需要前置防护——它们很短且始终以重新激活结束，因此未防护的窗口可以忽略不计（上面的首次推送和下面的长时间关闭是需要先设防护的）。批次是渐进的可见性，而不是正确性机制：关闭保证最终状态，所以不要在批次组成上纠结——提前推送然后后续重新修改的组件只需重新推送。

### 关闭——在子技能的最终门禁之后

1. **先哨兵，然后完整内容写入。** 在任何其他操作之前重新写入 `_ds_needs_recompile`——应用在用户打开项目时会清除哨兵（此路径在运行中邀请用户打开），而关闭是最长的写入+删除阶段，因此在此处重新防护是防止半应用状态被消费的关键。然后写入计划中除 `_ds_sync.json` 之外的所有内容，分块。重新上传未变更的文件是幂等且廉价的；此过程覆盖批次遗漏的任何内容和最终重建变更的任何内容，因此无论批次过程如何，项目最终与最终验证的构建完全一致。
2. **协调删除——强制性的，不是可选的。** `DesignSync(list_files)` 项目，然后 `delete_files` 在 `components/`、`_preview/`、`tokens/`、`fonts/`、`_vendor/`、`guidelines/` 下最终 `ds-bundle/` 中不存在的每个远程路径（计划的删除 glob 覆盖它们——无需新提示）。此过程存在的原因：由早期批次上传然后后续在运行中被丢弃、重命名或重新分组的组件，对未来的每次重新同步差异都不可见——基于锚点的差异只能看到锚点记录的内容——所以这是唯一可以清理它的时刻；跳过它，孤立文件就是永久的。删除操作还会退役孤立文件的卡片：应用从当前上传的文件重建其组件索引，因此一旦哨兵被重新激活（下一步）并且项目被打开，卡片就会消失。
3. **重新激活哨兵，然后 `_ds_sync.json` 绝对最后**，在其自身的 `write_files` 调用中——与原子路径相同的规则、相同的原因：锚点只能为完全应用的状态担保，它放在删除之后，以便失败的删除不会留下锚点不再看到的远程文件。然后输出项目 URL——`https://claude.ai/design/p/<projectId>`——附带最终摘要。

此路径上任何位置的中途中止（用户停止运行、会话死亡）使项目处于**未锚定**状态——已记录的 safe 状态：下一次同步重新验证所有内容并重新上传，不会有任何东西悄悄腐烂。与子技能上传章节一样，任何重试无法清除的写入/删除失败意味着**停止**——不重新激活哨兵，不写 `_ds_sync.json`。

## 编写约定头部

你刚刚花了大量精力让这个设计系统的预览正确渲染——弄清楚组件需要如何包装、需要什么 provider 和主题设置、加载顺序的重要性，以及哪些错误会悄悄产生无样式输出。这些知识在同步结束时如果不写下来就会蒸发，所以要写给一个非常特定的读者。

**谁会读它。** 你编写的文件被前置到生成的 README（通过 `readmeHeader` 配置键）并内联到*设计代理*的系统提示词中——一个使用此组件库构建应用的模型，数百次，为从未见过此文件的用户。它不会制作 storybook 预览、运行此仓库的构建或阅读其源码；它获得 README 和绑定的产物，没有别的东西。处于那个位置的代理遵循具体、列举的指导，无法遵循不存在的指导：命名设计令牌，它就会使用令牌；类词汇表未命名，它不会猜测你的——它会发明自己的。说用 provider 包装，它就会包装；不说，大多数情况下它不会。所以每一句话都必须通过一个测试：*设计代理能否在不猜测的情况下据此行动？*（"遵循设计系统的约定"通不过这个测试；删除它并写出约定。）

**写什么**——四个关注点，以适合此设计系统的任何结构组织：

- **包装和设置。** 如果组件需要 provider/根包装才能有样式（通常是设计令牌和主题所在之处），命名它，说明没有它会怎样，并在最小片段中展示包装——加上主题设置、加载顺序，以及任何让你在预览调试中耗费了一个周期的坑。按读者职责过滤：它构建应用，不是构建预览——特定于工具的设置（storybook 怪癖、脚手架）放入 NOTES.md；与构建组件相关的内容放入此处。
- **样式习惯，使用其实际词汇。** 教授此系统的习惯，绝不教授通用习惯：工具类系统获得紧凑的族表，使用样式源中的真实名称（Tailwind preset 精确枚举它们）；prop/主题系统获得"无 CSS 类——通过 props 设置样式"，带有承载设计语言的 props；设计令牌系统获得 `var(--*)` 模式及真实名称。绝不引入设计系统没有的习惯。
- **真理所在之处。** 命名代理在样式化之前应阅读的样式表/源文件（它拥有的绑定副本，例如 `_ds/<folder>/styles.css` 及其导入）以及每个组件的文档。阅读真实文件的代理胜过任何摘要——你的工作是确保它知道在哪里找。
- **一个惯用的构建片段。** 一个简短的、真实的示例——控件使用库组件，代理自身的布局胶水使用设计系统的样式习惯。改编你已验证的预览之一：这是你知道能渲染的代码。

不同类型的系统看起来像（示例性而非穷举性）：Tailwind-preset 设计系统 → 族表（`bg-surface-1`、`gap-md`、`text-body`……）+ 根包装；grommet 风格设计系统 → 无类名，`pad`/`background`/`tone` props + ThemeProvider；chakra 风格设计系统 → 主题令牌字符串（`color="red.500"`）；CSS-modules/BEM 设计系统 → 导出的类映射以及新名称是否合理；web-components 设计系统 → slots、属性和注册顺序。

**在交付前验证。** 命名了不存在内容的约定文件比没有更糟——代理会信任它，写出无法解析的词汇，并悄悄交付无样式输出。在提交之前：你枚举的每个类、令牌、prop 和组件必须存在于构建产物中——对照输出目录中编译的样式表 grep 类/令牌；对照输出目录中的 `components/<group>/<Name>/` 目录检查命名的组件（你刚运行的构建为每个组件生成一个——该树是同步时的名称索引；`.ds-build-meta.json` 只包含计数），然后在打包文本中检查（权威——例如像根包装这样的 provider 在打包中交付但不一定有组件文件夹），然后才提出声明。两者都验证不到 → 修复名称或删除它；源码中有记录但构建中不存在 → 这是 NOTES.md 发现，不是头部内容。

**篇幅。** 简洁——2-4k 字符覆盖所有四个关注点，真实名称胜过模糊表述。如果构建的大小警告触发，阅读是哪个方面。头部方面（仅头部就超过 ~31.9k）：缩短头部——它只有在自身适合 ~32k 窗口时才在截断中存活；超过后，其尾部被截断，正文不再贡献任何内容。正文方面：你的约定是安全的（前置的，在窗口内）；丢失的是生成正文的末尾——通常是组件索引的尾部。要么刻意接受这个损失，要么减少同步范围（package 形态：`componentSrcMap` 排除、更窄的 `tokensGlob`；storybook 形态：同步更少的 stories）——没有正文部分的裁剪旋钮。

**它存在的位置以及重新运行。** 编写 `.design-sync/conventions.md`，设置 `"readmeHeader": ".design-sync/conventions.md"`，提交两者——这是特意设计为人类可编辑的。然后重新构建，使 README 实际携带头部——它在构建时拼接。**重建规则：** 编写后的重建在任何路径上都是一次新的 DRIVER 运行——首次同步省略 `--remote`——因为关闭回执和上传计划都必须描述携带头部的构建；裸转换器运行会擦除 `.sync-diff.json` 和回执产物，使上传的构建没有回执。（所有其他提及编写后重建的地方都遵循此规则。）每当文件已存在——无论本次运行如何分类（重新同步、配置丢失后的重新采用、从部分配置恢复）：绝不重写它——对照新构建重新运行验证过程，报告任何不再能验证的名称（NOTES.md + 用户），提出编辑建议。编写仅发生在没有 `.design-sync/conventions.md` 时。内容属于其作者；你的持续职责是保持其真实性。
