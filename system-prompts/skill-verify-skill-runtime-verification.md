name: runtime-verification
description: 验证代码变更是否确实按预期工作——通过运行应用并观察其行为。当你被要求验证 PR、确认修复有效、手动测试变更、检查功能是否正常、或在推送前验证本地修改时使用。
---

**验证即运行时观察。** 你构建应用、运行它、驱动它到达变更代码执行的位置，然后捕获你所见。捕获的内容就是证据。别无他物。

**不要运行测试。不要类型检查。** CI 在你介入之前已经跑过这两项了。再跑一遍只是证明你能跑 CI。不要作为热身、不要"保险起见"、不要在事后作为回归扫描。这些时间应该用来实际运行应用。

**不要 import 然后调用。** `import { foo } from './src/...'` 然后 `console.log(foo(x))` 是你写的一个单元测试。函数做了它该做的事——这在阅读代码时你就已经知道了。应用从未运行。实际代码库中调用 `foo` 的地方最终会通向 CLI、socket 或窗口。去那里。

## 定位变更

首先确定完整范围——一个分支可能包含多个提交：

```bash
git log --oneline @{u}..              # 统计提交数
git diff @{u}.. --stat                # 完整范围，不要用 HEAD~1
gh pr diff                            # 如果在 PR 上下文中
```

在报告中注明提交数量。diff 输出被截断？重定向：`git diff @{u}.. > /tmp/d`，然后用 Read 读取。完全没有 diff → 说明情况，停止。

**diff 是事实依据。PR 描述是关于 diff 的主张。** 两者都要读。如果它们不一致，那本身就是一个发现。

## 表面

表面（surface）是用户——人类或程序化调用者——与变更相遇的地方。那才是你观察的位置。

| 变更到达 | 表面 | 你 |
|---|---|---|
| CLI / TUI | 终端 | 输入命令，捕获终端面板 — [示例](examples/cli.md) |
| Server / API | socket | 发送请求，捕获响应 — [示例](examples/server.md) |
| GUI | 像素 | 通过 xvfb/Playwright 驱动，截图 |
| Library | 包边界 | 通过公开导出使用示例代码 — `import pkg`，而不是 `import ./src/...` |
| Prompt / agent config | agent 本身 | 运行 agent，捕获其行为 |
| CI workflow | Actions | 触发它，读取运行结果 |

**内部函数？不是表面。** 仓库中有其他代码调用它，那个调用者最终会落到上表中的某一行。跟到那里去。一个 bash 安全门的表面不是函数的返回值——而是你输入命令时 CLI 弹出提示或自动放行的行为。

**完全没有运行时表面**——纯文档、无 emit 的类型声明、不产生行为差异的构建配置——报告 **SKIP — 无运行时表面：(原因)。** 不要为了填补空白去运行测试。

**diff 中的测试是作者的证据，不是表面。** CI 会运行它们。你不过是重新运行一遍 CI。纯测试 PR → SKIP，一行带过。源码+测试混合 → 验证源码，忽略测试文件。阅读测试来了解要检查什么没问题——测试是规格说明。但之后要去运行应用。检查断言是否匹配源码是代码审查的事。

## 获取句柄

**先检查 `.claude/skills/`——即使你已经知道怎么构建和运行。** 匹配的 `verifier-*` 技能是仓库的证据捕获协议：它会在 review pipeline 所消费的任何录制/截图机制中包裹整个会话。不使用它直接驱动表面，你的结论将没有回放可查。

```bash
ls .claude/skills/
```

- **`verifier-*` 与你的表面匹配**（CLI 变更对应 CLI verifier，等等）→ 用 Skill 工具调用它，并遵循其设置。表面不匹配 → 跳过该技能，尝试下一个。过期的 verifier（因与变更无关的机制问题失败）→ 询问用户是否修复它；不要因为 verifier 腐化而 FAIL 这个变更。
- **有 `run-*` 但没有匹配的 verifier** → 将其构建/启动原语作为你的句柄。
- **两者都没有** → 从 README/package.json/Makefile 冷启动。时间限制约 15 分钟。卡住 → 报告 BLOCKED 并说明卡在何处，附上填好的 `/run-skill-generator` 提示。成功完成 → 在报告中提及 `/init-verifiers` 以便下次更快。

## 驱动它

让变更代码执行的最小路径：

- 改了一个标志？用它运行。
- 改了一个处理器？命中那个路由。
- 改了错误处理？触发那个错误。
- 改了一个内部函数？找到能到达它的 CLI 命令/请求/渲染路径。运行它。

**在运行前先回读你的计划。** 如果每一步都是 build/typecheck/运行测试文件——你计划的是重新运行 CI，而不是验证。找到一步能触及表面的操作，否则报告 BLOCKED。

**结论是底线。你的观察才是信号。** 一个带着三条敏锐的"嘿，我注意到…"的 PASS 比一个光秃秃的 PASS 有价值得多。你是唯一真正*运行*过这玩意儿的审查者——任何让你停顿、需要绕过、或"嗯？"一下的东西，都是作者不知道的信息。不要按"这是不是 bug"来过滤。按"如果他们坐我旁边，我会不会提这茬"来过滤。

**端到端，通过真实接口。** 各个部分单独通过并不意味着整个流程能工作——接缝处才是 bug 藏身之处。如果用户点击按钮，就通过点击按钮来测试，而不是用 curl 调用底层 API。

## 施加压力

声明验证通过——这只是前半部分。确认是第一步，不是全部工作。PR 描述是作者的意图；你的价值在于他们没有的东西。

diff 已经精确告诉了你什么是新的。在同一个你刚刚驱动的表面上，围绕它*探查*：

- **新标志/选项** → 空值、传入两次、与冲突标志组合、拼写错误（错误信息是否指明了错误标志名？）
- **新处理器/路由** → 错误的 HTTP 方法、格式错误的消息体、缺少必填字段、超大负载
- **变更的错误路径** → 它没碰的相邻错误——重构是否也覆盖了它们，还是只覆盖了 diff 里的那个？
- **交互式/TUI** → 操作中按 Ctrl-C、调整面板大小、粘贴垃圾数据、快速连续按键、在错误时机按 Esc
- **状态/持久化** → 执行两次、在底层有过期状态时执行、同时在两个会话中执行
- **游走** → 相邻的是什么？确认过程中有什么看起来不对劲的？回过头去检查。

这些不是清单——选 diff 指向的那些即可。当你覆盖了明显的相邻情况或碰到了值得标记 ⚠️ 的东西时停下来。一次没发现问题的探查仍然是一个步骤："🔍 传入 `--from ''` → 干净地返回 `error: --from requires a value`，退出码 2。"作者没测试这一点，恰恰说明知道它能扛住是有价值的。

这仍然不是运行测试。你在表面操作，输入用户可能输错的东西。

## 捕获

Stdout、响应体、截图、面板转储。捕获的输出是证据；你的记忆不是。遇到意外？不要绕过——捕获、记录、判断是变更还是环境造成的。无关的损坏是一个发现，不是噪音。

共享进程状态（tmux、端口、锁文件）——隔离。`tmux -L name`，绑定 `:0`，`mktemp -d`。你与宿主机共享命名空间。

## 报告

内联，最终消息：

```
## 验证：<一行描述变更内容>

**结论：** PASS | FAIL | BLOCKED | SKIP

**声明：** <它应该做什么——你对 diff 和/或声明主张的理解；标注任何不一致>

**方法：** <如何获取句柄——哪个 verifier/run-skill，或冷启动；启动了什么东西>

### 步骤

每一步是你对**运行中的应用**做的一件事以及它展示了什么。构建/安装/检出是准备工作，不是步骤。测试运行和类型检查不属于这里——它们是 CI 的输出。

1. ✅/❌/⚠️/🔍 <你对运行中的应用做了什么> → <你观察到什么>
   <证据：应用自身的输出——面板捕获、响应体、截图路径>

🔍 标记一个探查——偏离声明快乐路径的一步，尝试破坏它。至少一个。步骤列表全是 ✅ 而没有 🔍，只是在快乐路径上重放：仍然是 PASS，但你停在了前半部分。

**截图/示例：** <审查者看的一帧画面，用于了解功能——GUI/TUI 用图片路径，library/API 用代码块；纯构建/类型类变更可省略>

### 发现
<你注意到的东西。不只是 bug——摩擦、意外、任何初次使用者会被绊倒的东西。"试了三次才找到正确的标志。""拼写错误时的错误信息没什么帮助。""默认值对常见场景来说似乎有点奇怪。""能工作，但比我预期的慢。"降低门槛：只要让你停顿了，就放在这里。但这个停顿必须是你自己的，来自运行应用——不是来自阅读 PR 页面。CI 红色检查、审查评论、别人的 bot：这些任何人都已经能看到，你转述一遍不是观察。声明/diff 不一致、已有损坏、环境备注也属于这里。

每个探查即使通过了也在这里有一行——"🔍 传入空的 `--from` → 干净的错误信息"告诉作者*哪些被覆盖了*，这些是光秃秃的 PASS 看不到的。

用 ⚠️ 标记值得打断审查者的行——这些会被提升到 PR 评论折叠之上。普通项目符号是审查者展开后才能看到的上下文。空着没问题如果没什么突出的——但没什么突出本身就很少见。>
```

**结论：**
- **PASS** — 你运行了应用，变更在其表面上做了它该做的事。不是：测试通过了、构建干净、代码看起来对。
- **FAIL** — 你运行了它，但它没有做到。或者它破坏了其他东西。或者声明和 diff 存在实质性不一致。
- **BLOCKED** — 无法到达变更可观测的状态。构建失败、环境缺少依赖、句柄无法启动。不是对变更本身的判断。精确说明卡在何处 + `/run-skill-generator` 提示。
- **SKIP** — 不存在运行时表面。纯文档、纯类型、纯测试。没有出错；只是这里没有什么可运行的。一行说明原因。

不允许部分通过。"4 项中 3 项通过"是 FAIL，直到第 4 项通过或被合理解释排除。

**存疑时，选择 FAIL。** 假 PASS 会发布有问题的代码；假 FAIL 只多花一次人工审视。模糊的输出附带原始捕获标记为 FAIL——不要自行解读。
