---
name: verify
description: 验证代码更改是否按预期工作，通过运行应用并观察行为。当被要求验证 PR、确认修复有效、手动测试更改、检查功能是否正常，或在推送前验证本地更改时使用。
---

**验证即运行时观察。** 你构建应用，运行它，
驱动它到达被更改代码的执行点，然后捕获你所看到的。
那个捕获就是你的证据。其他都不是。

**不要运行测试。不要类型检查。** 在这里运行它们只能证明你能运行 CI——不能证明更改有效。不作为热身，
不"以防万一"，不作为事后回归检查。时间应该花在运行应用上。

**不要导入并调用。** `import { foo } from './src/...'` 然后
`console.log(foo(x))` 是你写的一个单元测试。函数做了它该做的——
你从阅读代码就知道了。应用从未运行过。
在真实代码库中调用 `foo` 的任何调用者最终都会到达一个 CLI、一个 socket 或
一个窗口。去那里。

## 找到更改

范围是你正在验证的内容——通常是一个 diff，有时只是
"X 是否工作。" 在 git 仓库中，确定完整范围（一个分支可能包含多个提交，或者更改可能仍未提交）：

```bash
git log --oneline @{u}..              # 统计提交数（如果已设置上游）
git diff @{u}.. --stat                # 完整范围，而非 HEAD~1
git diff origin/HEAD... --stat        # 无上游：已提交 vs 基准
git diff HEAD --stat                  # 未提交：工作树 vs HEAD
gh pr diff                            # 如果在 PR 上下文中
```

说明提交数量。大 diff 被截断？重定向到文件然后读取它。有仓库但以上命令均无 diff → 说明情况，停止。
**无仓库 → 范围就是用户指定的任何内容；如果他们没有指定，询问。**

**Diff 是事实依据。任何描述都是对它的声明。**
两者都读。如果它们不一致，那就是一个发现。

## 表面

表面是用户——人或程序——与更改相遇的地方。那就是你观察的地方。

| 更改到达 | 表面 | 你的操作 |
|---|---|---|
| CLI / TUI | 终端 | 输入命令，捕获面板——[示例](examples/cli.md) |
| 服务端 / API | socket | 发送请求，捕获响应——[示例](examples/server.md) |
| GUI | 像素 | 在 xvfb/Playwright 下驱动它，截图 |
| 库 | 包边界 | 通过公共导出的示例代码——`import pkg`，而非 `import ./src/...` |
| 提示词 / 代理配置 | 代理 | 运行代理，捕获其行为 |
| CI 工作流 | Actions | 触发它，读取运行日志 |

**内部函数？那不是表面。** 仓库中的某些东西调用了它，
那个调用者最终会到达上述某一行。顺着它去那里。一个
bash 安全门的表面不是函数的返回值——它是
CLI 在你输入命令时提示或自动允许。

**根本没有运行时表面**——仅文档、无产出的类型声明、
不产生行为差异的构建配置——报告
**SKIP——无运行时表面：（原因）。** 不要运行测试来填补空间。

**Diff 中的测试是作者的证据，不是表面。** CI
会运行它们。你只是在重新运行 CI。仅测试的 PR → SKIP，一行。
混合 src+测试 → 验证 src，忽略测试文件。阅读
测试以了解要检查什么是可以的——它就是一个 spec。但之后要去
运行应用。检查断言是否与源代码匹配是代码审查。

## 获取句柄

**优先检查 `.claude/skills/` —— 即使你已经知道如何构建和运行。** 匹配的 `verifier-*` 技能是仓库的证据捕获协议：它将会话包装起来，使审查者可以重放你所看到的（录制、截图）。不通过它驱动表面，你只能得到没有回放的结论。

```bash
ls .claude/skills/
```

- **`verifier-*` 匹配你的表面**（CLI 更改对应 CLI 验证器等）→ 使用 Skill 工具调用它并遵循其设置。表面不匹配 → 跳过它，尝试下一个。过时的验证器（在与更改无关的机制上失败）→ 询问用户是否要修补它；不要因为验证器腐烂而 FAIL 更改。
- **`run-*` 但没有匹配的验证器** → 使用其构建/启动原语作为你的句柄。
- **两者都没有** → 从 README/package.json/Makefile 冷启动。时间盒 ~15 分钟。卡住 → BLOCKED 并精确说明在哪里，加上一个填好的 `/run-skill-generator` 提示词。通过了 → 记下可行的构建/启动方案，以便将来可以变成 `verifier-*` 技能。

## 驱动它

使更改代码执行的最小路径：

- 更改了一个标志？带上它运行。
- 更改了一个处理器？访问那个路由。
- 更改了错误处理？触发那个错误。
- 更改了一个内部函数？找到到达它的 CLI 命令/请求/渲染。
  运行那个。

**在运行之前重读你的计划。** 如果每一步都是构建/
类型检查/运行测试文件——你计划了一次 CI 重新运行，而不是
验证。找到一个到达表面的步骤，否则报告 BLOCKED。

**结论只是入场券。你的观察才是信号。**
一个 PASS 带有三条尖锐的"嘿，我注意到…"的评论比一个
裸 PASS 更有价值。你是唯一实际*运行了*东西的审查者——
任何让你停顿、绕道或"嗯"了一下的事情都是信息，
作者不知道。不要过滤"这是 bug 吗。"过滤为
"如果他们坐在我旁边，我会提这个吗。"

**端到端，通过真实接口。** 在隔离中通过部分测试
并不意味着流程工作——接缝是 bug 藏身之处。
如果用户点击按钮，通过点击按钮测试，而不是通过 curl 下面的 API。

**破坏性路径？** 如果更改涉及的代码会删除、发布、发送或写入工作区之外，且没有 dry-run 或安全目标，不要直接驱动它。验证你能验证的周边部分，并说明你没有执行哪条路径以及原因。

## 推进

声明通过了——这只是前半部分。确认是第一步，
而不是工作本身。描述是作者意图的；
你的价值在于他们没考虑到的。

你精确知道哪些代码变了。在你刚刚驱动的同一个表面
*周围*探测：

- **新标志/选项** → 空值、重复传递、与冲突标志组合、拼写错误（错误是否命名了它？）
- **新处理器/路由** → 错误方法、格式错误的请求体、缺少必填字段、超大的负载
- **已更改的错误路径** → 它没有触及的相邻错误——重构也捕获了它们，还是只捕获了 diff 中的那个？
- **交互式 / TUI** → 中途 Ctrl-C、调整面板大小、粘贴垃圾、快速按键、在错误时机按 Esc
- **状态/持久化** → 做两次、在下方有陈旧状态时做、同时在两个会话中做
- **漫游** → 相邻的是什么？你在确认时什么看起来不对劲？回到那里。

这些不是清单——选择更改指向的那些。停止
当你覆盖了明显的相邻区域或遇到值得 ⚠️ 的内容时。
一个什么都没发现的探测仍然是一个步骤："🔍 传递 `--from ''`
→ 清晰的 `error: --from requires a value`，退出码 2。"作者
没有测试它正是为什么值得知道它能扛住的原因。

仍然不是测试运行。你在表面，输入用户
会输入错误的内容。

## 捕获

标准输出、响应体、截图、面板转储。捕获的输出是
证据；你的记忆不是。遇到了意外？不要绕过
它——捕获、记录、判断是更改还是环境的问题。
无关的破坏是一个发现，不是噪音。

共享进程状态（tmux、端口、锁文件）——隔离。`tmux -L
name`，绑定 `:0`，`mktemp -d`。你与主机共享命名空间。

## 报告

内联，最终消息：

```
## 验证：<一行说明更改了什么>

**结论：** PASS | FAIL | BLOCKED | SKIP

**声明：** <它应该做什么——你对 diff 的解读和/或
所述声明；记录任何不匹配>

**方法：** <你如何获得句柄——哪个验证器/run-skill，或
冷启动；你启动了什么>

### 步骤

每一步是你对**运行中的应用**所做的一件事以及它
显示的结果。构建/安装/检出是设置，不是步骤。测试运行和
类型检查不属于这里——它们是 CI 的输出。

1. ✅/❌/⚠️/🔍 <你对运行中的应用做了什么> → <你观察到了什么>
   <证据：应用自己的输出——面板捕获、响应体、
   截图路径>

🔍 标记探测——偏离声明主线、试图破坏它的步骤。至少一个。全是 ✅ 没有 🔍 的步骤列表是主线回放：仍算 PASS，但你只完成了前半部分。

**截图/示例：** <审查者看一眼就能看到功能的那一帧——
GUI/TUI 用图片路径，库/API 用代码块；
仅构建/类型时省略>

### 发现
<你注意到的事情。不仅仅是 bug——摩擦、意外、任何
首次用户会绊倒的事情。"找了三次才找到正确的标志。"
"拼写错误时的错误消息没有帮助。""默认值对常见情况似乎很奇怪。""能用，但比我预期的慢。"
降低标准：如果它让你停顿，就放在这里。但这个停顿必须是你的，
来自运行应用——而不是来自阅读 PR 页面。红色的 CI 检查、
审查评论、别人的 bot：对已经能看到的人来说是可见的，
你转述它不是观察。声明/diff 不匹配、预先存在的
破坏和环境说明也属于这里。

每条探测都有一行，即使它没出问题——"🔍 空 `--from`
→ 清晰的错误"告诉作者*哪些被覆盖了*，他们从裸 PASS 中是看不到的。

以 ⚠️ 开头表示值得打断审查者的行；普通项目符号是上下文。如果没什么突出的，空是可以的——但没什么突出的本身就很罕见。>
```

**结论：**
- **PASS** — 你运行了应用，更改在其表面上做了它应该做的。
  不是：测试通过、构建干净、代码看起来正确。
- **FAIL** — 你运行了它，但它不起作用。或者它破坏了其他东西。
  或者声明和 diff 存在实质性分歧。
- **BLOCKED** — 无法达到更改可观察的状态。
  构建失败、环境缺少依赖、句柄无法启动。这不是
  对更改的结论。精确说明在哪里停止 +
  `/run-skill-generator` 提示词。
- **SKIP** — 不存在运行时表面。仅文档、仅类型、
  仅测试。没有出问题；只是这里没有东西可以运行。
  一行说明原因。

没有部分通过。"4 个中通过 3 个"是 FAIL，直到 4 个全部通过或被
解释清楚。

**有疑问时，FAIL。** 错误的 PASS 会发布损坏的代码；错误的 FAIL
只多花一个人看一眼。模糊的输出是 FAIL 并附上原始
捕获——不要解读。
